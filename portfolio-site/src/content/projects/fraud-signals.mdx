## Problem

Fraud teams in telecom and fintech need to react in seconds, not hours. Batch
ETL surfaces a compromised account long after the money has moved. This
project is the streaming half of that problem: a producer publishes labeled
transaction events, Spark Structured Streaming lands them in Delta with a
watermark and checkpoint, and three detectors — velocity, impossible travel,
and amount outliers — score the stream. Because every synthetic event carries
its ground-truth label, detector quality is something the repo measures
rather than asserts.

## Judgment calls

**Why streaming over batch?** Fraud ages out fast. An anomaly that lands two
hours late is informational, not operational. The producer keys events by
`account_id`, which preserves per-account ordering in Kafka even when
consumers scale out.

**Why Spark Structured Streaming over Flink?** Flink has lower tail latency
and richer state primitives. I picked Spark because the lakehouse is already
Delta, so ingestion and analytics share one engine, and Structured
Streaming's batch-equivalent model matches how analytics teams already reason
in SQL. For sub-100 ms decisions, Flink would be the right call.

**Exactly-once, precisely.** The consumer appends to Delta with a checkpoint.
Delta's streaming sink records each micro-batch id in its transaction log, so
a batch replayed after a crash is recognised and skipped — that is what makes
the pipeline exactly-once *across the checkpoint boundary*. The 2-minute
watermark bounds how much late-event state Spark has to keep.

**Detectors stay framework-free.** The three detectors are plain Python
functions over event dicts, so they unit-test without a cluster and run the
same way in the evaluator, the Streamlit dashboard, or a future streaming
`foreachBatch`. Today they run in batch over the evaluation set; wiring them
into the streaming query is the next step, not something the demo claims.

## What I would do differently in production

- Replace the fixed velocity threshold with a per-account baseline, so
  precision holds up for naturally busy accounts.
- Swap per-account z-scores computed over the whole window for an online
  estimator (Welford or t-digest) to bound memory.
- Run the detectors inside the streaming query (`foreachBatch`) and write
  scored events to their own Delta table.
- Add a schema registry so producer/consumer compatibility is enforced at
  deploy time.
- Move the operator dashboard off Streamlit for anything customer-facing.
