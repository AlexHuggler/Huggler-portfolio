## Problem

There is a real gap between "a query that runs" and "a query a senior would
ship": knowing when to broadcast, prune partitions, flatten repeated scans,
or replace correlated subqueries. This tool parses Spark SQL and Snowflake
queries with sqlglot, runs a small set of heuristic rules over the AST, and
sends the SQL plus structured findings to Claude with a versioned optimizer
prompt. Without an API key it runs in a heuristics-only dry-run mode, which
is what the published benchmark measures.

## Judgment calls

**Heuristics + LLM, not LLM only.** Sent raw SQL, a model spends its budget
re-deriving facts a parser already knows: which columns are projected, which
joins lack hints, whether a subquery is correlated. A sqlglot pass extracts
those cheaply and ships them as structured findings, leaving the model to
decide what to do about them.

**EXPLAIN is the planned verifier, not a claimed one.** Cost estimates
reflect the planner's statistics and thresholds, so they make a tiebreaker
rather than ground truth. The EXPLAIN runner is designed in the methodology
doc but not implemented, and the site says so.

**Prompt sensitivity is a real risk.** Small prompt edits change suggestion
quality, so the prompt lives in version control
(`prompts/optimizer_prompt.md`) next to the code that sends it. Regression
tests that pin model output against the corpus are the next step.

**A corpus designed to grow.** Five categories, one fully specified query
each, with expected keywords and cost direction in `corpus/ground_truth.yaml`.
Adding a case is one `.sql` file plus one ground-truth entry.

## Honest limitations

- `benchmark --no-dry-run` does not call Claude yet, so model rewrite quality is unmeasured.
- Claude can hallucinate plausible column or table names that are not in the schema.
- The benchmark ignores each query's `-- engine:` header, so Snowflake queries are parsed as Spark.
- EXPLAIN cost deltas and human acceptance rate are planned, not run.
