## Problem

Telecom billing teams sit on enormous CDR (Call Detail Record) volumes and
need a single source of truth for revenue, ARPU, and churn signals. The
Medallion pattern — Bronze raw, Silver cleaned and rated, Gold
consumption-ready — keeps late-arriving data and vendor corrections
replayable while exposing only clean marts to BI. This project implements
the whole path: a synthetic CDR generator, three Airflow DAGs, S3-compatible
storage, a Great Expectations contract at the Bronze boundary, eight dbt
models, and Terraform for the AWS variant — all runnable locally without an
AWS account.

## Judgment calls

**Why medallion over a single table?** Keeping Bronze append-only means a
schema change, a parsing bug, or a vendor correction can be replayed without
re-ingesting from upstream. Silver is where typing, validity filters, and
rating (billable minutes and megabytes) happen. Gold is the only layer BI
tools read.

**Iceberg vs Delta.** Both work. Iceberg's hidden partitioning and partition
evolution make schema migrations less painful, and it keeps the tables
portable to Trino or Athena. In a Spark-only shop Delta is an equally good
choice; for a batch-first billing workload read by several engines, Iceberg
is the cleaner fit.

**A contract at Bronze, tests at Silver and Gold.** The Great Expectations
suite specifies what may enter the lake — exact column set, non-null keys, the
`^\+1[0-9]{10}$` MSISDN pattern, accepted values, numeric ranges. dbt tests
then guard what the models produce — uniqueness, accepted values,
non-negative revenue, and a `relationships` check from Silver back to the
account register. Honest caveat: the `transform_silver` DAG loads the GE
context but does not run a checkpoint yet, so the contract is defined and
version-controlled but not enforced at runtime.

**Independent schedules, on purpose for now.** Ingest and Silver run hourly
and Gold daily, each as its own DAG with retries. Nothing links them yet;
production would add Airflow Datasets so Gold rebuilds only when Silver has
actually changed.

## Measured results

`make demo` takes {ev.rowCounts.silver.toLocaleString("en-US")} synthetic CDRs across
{ev.partitions} daily partitions from raw parquet through Bronze, Silver, and three Gold
marts; the transform itself runs in {metric("telecom.transform").value} (median of
{ev.transform.runs} in-process runs on DuckDB). `dbt build` over the same raw data builds all
{ev.dbt.models} models and passes {metric("telecom.dbt").value} tests. The project vendors
local replacements for its two dbt_utils macros, so it runs completely offline.

One result is a finding rather than a success: the generator draws a fresh
random MSISDN for every record, so each caller appears exactly once and the
`churn_signals` mart classifies every caller as high risk. The SQL is right;
the synthetic data isn't shaped for it. The fix — a fixed subscriber pool —
belongs in the generator.

## What I would do differently in production

- Run the GE checkpoint for real (or move to GE 1.x / `pandera`) so a broken
  contract blocks the Silver build.
- Link the DAGs with Airflow Datasets and emit OpenLineage from every task
  and dbt run.
- Add cross-column contracts (e.g. roaming only on roaming-eligible plans).
- Replace LocalExecutor with KubernetesExecutor for scale-out.
- Add an Iceberg compaction DAG to keep Bronze file counts bounded.
